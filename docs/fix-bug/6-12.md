# 2026-06-12 EVM 链配置规范化：支持 Anvil / localhost / 自定义 Chain

## 背景问题

当前 `snk-wallet-kit` 的 EVM 链配置仍然是“字符串白名单”模型：

- `evm.chains` 在类型上是 `string[]`
- 内部只映射 `mainnet` / `sepolia`
- `createWalletKitEvmConfig` 只能生成预置链对应的 wagmi config

这会直接带来几个问题：

1. 不能自然支持 `anvil` / `localhost` / 私链
2. 不能自然支持 Base、Arbitrum、Optimism 等更多主流 EVM 链
3. 宿主项目如果已经有自己的 `Chain` 定义，无法直接复用
4. 库的 API 不够贴近当前主流 web3 npm 库的设计习惯

从 npm 库规范和生态兼容性来看，这一层不应该自己发明一个过于封闭的链配置 DSL，而应该尽量复用 `viem` / `wagmi` 的上游类型体系。

---

## 推荐设计目标

这次改造的目标不是“只给 Anvil 开个特例”，而是把 EVM 链配置收敛为更符合主流规范的模型：

1. **底层能力直接兼容 `viem` 的 `Chain` 类型**
2. **保留预置链名作为便捷写法**
3. **让 `createWalletKitEvmConfig` 成为 wagmi config 的薄封装，而不是封闭工厂**
4. **让 `WalletCoreProvider` 成为自定义链场景的稳定高级接入方式**
5. **避免未来每多支持一条链都要改一轮类型和映射表**

---

## 推荐方案

### 方案核心：`evm.chains` 支持双模式输入

推荐将当前的：

```ts
chains?: string[];
```

升级为类似：

```ts
import type { Chain } from "viem";

type PresetEvmChain = "mainnet" | "sepolia";

type EvmChainInput = PresetEvmChain | Chain;

type EvmConfig = {
  enabled?: boolean;
  chains?: EvmChainInput[];
  wallets?: EvmWalletId[];
  reconnectOnMount?: boolean;
  walletConnectProjectId?: string;
  coinbaseAppName?: string;
};
```

也就是：

- 简单用户仍然可以写 `"mainnet"`、`"sepolia"`
- 高级用户可以直接传 `defineChain(...)` 生成的 `Chain` 对象
- Anvil / localhost / 私链 / L2 / 测试链都自然落在第二类

这是目前最符合主流 npm 库习惯的方案：

- **易用性**：保留预置字符串
- **可扩展性**：直接兼容上游 `Chain`
- **学习成本低**：高级用户不需要重新学一套链定义语法

---

## 为什么这是更符合主流规范的设计

### 1. 尽量复用上游类型，而不是重新定义封闭抽象

在 web3 React 生态里，`viem` 的 `Chain` 已经是事实标准之一。

如果库内部只接受：

- `"mainnet"`
- `"sepolia"`
- 后续再人工补 `"anvil"`
- 再补 `"base"`
- 再补 `"arbitrum"`

这种模式很快就会演变成：

- 类型不断膨胀
- 文档不断补例外
- 用户仍然无法覆盖自己的私有链

更合理的方式是：

- 预置链名只做 convenience layer
- 真正的扩展能力直接交给 `Chain`

这和大部分现代 npm 库的设计原则一致：

- **默认体验简单**
- **高级场景不封死**
- **与上游生态对象模型对齐**

---

### 2. 不要把链能力锁死在库自己的 `CHAIN_MAP` 上

当前内部的 `CHAIN_MAP` 只适合 demo 级别：

```ts
const CHAIN_MAP = {
  mainnet,
  sepolia,
} as const;
```

如果目标是一个可复用的 npm 库，链列表不应该成为库升级节奏的瓶颈。

更推荐的策略是：

- 保留一个 `PRESET_CHAINS`
- 但解析时允许对象透传

类似：

```ts
const PRESET_CHAINS = {
  mainnet,
  sepolia,
} as const;

function resolveChain(input: EvmChainInput): Chain | null {
  if (typeof input === "string") {
    return PRESET_CHAINS[input] ?? null;
  }
  return input;
}
```

这样既保留了库层面的便捷能力，也避免把扩展能力绑死在内部白名单。

---

### 3. Anvil 应该被视为“自定义链自然支持”，而不是“特殊兼容项”

从设计上讲，Anvil 不值得单独做一条特殊分支。更合理的说法是：

- 只要支持标准 `Chain`
- 那么 Anvil、localhost、Hardhat Network、企业私链都自动成立

示例：

```ts
import { defineChain } from "viem";

export const anvil = defineChain({
  id: 31337,
  name: "Anvil",
  nativeCurrency: {
    name: "Ether",
    symbol: "ETH",
    decimals: 18,
  },
  rpcUrls: {
    default: {
      http: ["http://127.0.0.1:8545"],
    },
  },
});
```

然后用户可以直接：

```ts
const config = {
  evm: {
    enabled: true,
    chains: [anvil],
    wallets: ["metaMask"],
  },
};
```

这比新增一个 `"anvil"` 字符串常量更符合长期演进方向。

## API 设计建议

### 方案 A：推荐方案

#### 1. `evm.chains` 支持 `PresetEvmChain | Chain`

这是最推荐的对外 API。

优点：

- 对新手友好
- 对高级用户友好
- 向上兼容现有配置风格
- 易于在 README 里解释

#### 2. 导出预置链类型或常量

可以考虑额外导出：

```ts
export type PresetEvmChain = "mainnet" | "sepolia";
```

或者：

```ts
export const walletKitPresetChains = {
  mainnet,
  sepolia,
};
```

这样可以让消费方更明确知道：

- 哪些是库内预置
- 哪些应该直接走 `viem` 的 `Chain`

#### 3. `createWalletKitEvmConfig` 保持薄封装定位

`createWalletKitEvmConfig` 的职责建议收敛为：

- 读取 `evm.chains`
- 解析成 `Chain[]`
- 生成 connectors
- 生成 wagmi config

不要让它再承担“链枚举定义中心”的角色。

它应该是一个 **方便创建 wagmi config 的 helper**，不是一个封闭的链管理系统。

---

### 方案 B：只接受 `Chain[]`

另一种更极致的方案是：

```ts
chains?: Chain[];
```

即完全不再接受字符串。

优点：

- API 最纯粹
- 完全对齐上游
- 内部实现最简单

缺点：

- 快速上手体验变差
- README 示例会更长
- 对轻量用户不够友好

结论：

- 如果这个库定位是“偏底层基础设施库”，可以考虑
- 但如果仍然想保持“开箱即用”的产品感，**不如双模式更平衡**

---

### 方案 C：继续字符串白名单，但不断扩容

例如继续这样演进：

```ts
type PresetEvmChain =
  | "mainnet"
  | "sepolia"
  | "anvil"
  | "base"
  | "arbitrum"
  | ...
```

不推荐。

问题在于：

- 每支持一条链都要发版
- 永远覆盖不完真实世界需求
- 私链仍然无解
- 用户会困惑“为什么 wagmi 支持，但你这个库不支持”

这不符合现代 npm 库应有的开放性。

---

## Provider 规范建议

### 推荐把 `WalletCoreProvider` 作为自定义链场景的正式推荐路径

目前库里已经有 `WalletCoreProvider` + 外部 `wagmiConfig` 模式，这其实非常适合作为高级用法标准入口。

建议在文档里明确分层：

#### 模式 1：快速接入

- 使用 `WalletProvider` / `WalletKitProvider`
- 适合只用预置链的项目
- 适合 demo / 简单业务场景

#### 模式 2：宿主管理 wagmi

- 使用 `WalletCoreProvider`
- 宿主自己创建 `wagmiConfig`
- 适合 Anvil / localhost / 私链 / 多环境 / 自定义 transport / 更复杂的链路控制

如果 README 里把第二种模式明确标为：

- **高级模式**
- **推荐用于自定义链和生产级集成**

那么整个 API 心智会更清晰，也更贴近 RainbowKit / wagmi 生态的使用习惯。

---

## 推荐实施步骤

### 第 1 步：修改类型定义

将 `src/core.ts` 中的：

```ts
chains?: string[];
```

改为：

```ts
import type { Chain } from "viem";

export type PresetEvmChain = "mainnet" | "sepolia";
export type EvmChainInput = PresetEvmChain | Chain;

chains?: EvmChainInput[];
```

同时把 `NormalizedWalletKitConfig` 对应字段类型同步更新。

---

### 第 2 步：重构链解析逻辑

将当前 `CHAIN_MAP` + `resolveChains` 的逻辑改成：

- 字符串走预置映射
- 对象直接透传
- 保证最终产出 `[Chain, ...Chain[]] | null`

伪代码：

```ts
function resolveChain(input: EvmChainInput): Chain | null {
  if (typeof input === "string") {
    return PRESET_CHAINS[input] ?? null;
  }
  return input;
}

function resolveChains(config: NormalizedWalletKitConfig): [Chain, ...Chain[]] | null {
  if (!config.evm.enabled) return null;

  const resolved = config.evm.chains
    .map(resolveChain)
    .filter(Boolean) as Chain[];

  if (!resolved.length) return null;
  return resolved as [Chain, ...Chain[]];
}
```

---

### 第 3 步：补充文档与示例

README 至少应补三类示例：

1. **预置链示例**
   - `chains: ["mainnet", "sepolia"]`

2. **Anvil 示例**
   - `defineChain(...)`
   - `chains: [anvil]`

3. **`WalletCoreProvider` 高级集成示例**
   - 宿主创建自己的 wagmi config
   - kit 只消费这套 config

这样用户就不会再问“这个库为什么不能连 localhost”。

---

### 第 4 步：明确版本策略

虽然双模式方案大概率可以做到向后兼容，但它本质上是一个重要 API 扩展。

建议至少按以下方式处理：

- 如果保持旧字符串写法完全可用：发 **minor** 版本
- 如果顺带重命名/重构链配置相关 API：发 **major** 或新的 0.x 次版本里显式说明 breaking change

如果后续计划继续做 Provider ownership 收敛，这个版本最好把“链配置规范化”和“高级接入路径说明”一起发布。

---

## 验收标准

### 类型层面

- `evm.chains` 支持 `"mainnet"` / `"sepolia"`
- `evm.chains` 也支持标准 `Chain` 对象
- TypeScript 提示清晰，不需要用户写额外 hack

### 能力层面

- 可以配置并连接 Anvil / localhost
- 可以配置并切换到任意自定义 EVM 链
- 不需要为每条新链修改库源码

### 文档层面

- README 明确区分“预置链模式”和“自定义链模式”
- README 明确推荐 `WalletCoreProvider` 作为高级集成方案
- 示例覆盖至少一个本地链场景

### 架构层面

- `createWalletKitEvmConfig` 成为 wagmi config helper，而不是封闭链工厂
- 内部链支持不再受限于固定白名单
- 未来扩展新链时不需要继续膨胀库自己的字符串枚举

---

## 最终建议结论

如果目标是让 `snk-wallet-kit` 更符合目前流行的 npm 库规范，最推荐的设计是：

1. **`evm.chains` 采用 `PresetEvmChain | Chain` 双模式输入**
2. **保留预置字符串作为便捷层，不再把它当成唯一能力边界**
3. **将自定义链支持视为标准能力，而不是 Anvil 特判**
4. **让 `WalletCoreProvider` 成为自定义链 / 生产级集成的正式推荐模式**
5. **让 `createWalletKitEvmConfig` 回归“helper”角色，尽量复用 wagmi / viem 官方模型**

这是在“开箱即用”和“生态兼容性”之间最平衡、也最符合现代 web3 npm 库设计习惯的方案。
