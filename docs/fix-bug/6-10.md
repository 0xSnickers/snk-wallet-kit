# 2026-06-10 重构清单：snk-wallet-kit 规范化改造优先级

## 目标

将 `snk-wallet-kit` 从“项目内可用的钱包封装”收敛为“可复用的 npm 钱包连接库”，重点解决以下问题：

1. 宿主应用与库内出现两套 `wagmi` / `@wagmi/core` 状态源
2. Provider 责任不清，连接生命周期被重复接管
3. 自动重连、会话持久化、手动连接三套逻辑相互叠加
4. 当前实现可用，但不够符合类似 RainbowKit 的生态规范

---

## 推荐架构决策

### 推荐路线：收敛为“UI + hooks + connector selection”层

`snk-wallet-kit` 的目标如果是“类似 RainbowKit”，更推荐采用下面这条路线：

- 宿主应用负责提供唯一的 `WagmiProvider` / `QueryClientProvider`
- `snk-wallet-kit` 只负责：
  - 钱包选择 UI
  - 连接按钮与弹窗
  - 钱包能力的轻量封装
  - EVM / Solana 的统一交互抽象
- `snk-wallet-kit` 不再拥有第二套 EVM 连接状态机
- EVM 的连接、重连、持久化尽量复用宿主的 wagmi 体系

### 不推荐继续维持的形态

当前这种“双模式混合”形态风险最高：

- 一方面提供 `WalletKitProvider` 自己创建 provider
- 另一方面又提供 `WalletCoreProvider` 接入宿主 provider
- 但内部仍然自己做 `connect/reconnect/watchConnection/session persistence`

这会导致谁拥有连接生命周期变得不清晰。

---

## 优先级总览

| 优先级 | 主题 | 结论 |
| --- | --- | --- |
| P0 | 依赖边界与状态所有权 | 必须先改，否则持续出现重复连接与版本冲突 |
| P1 | API 语义与重连模型收敛 | 解决配置混乱、降低接入误用概率 |
| P2 | Connector 实现与工程质量 | 提升稳定性、可维护性与发布质量 |
| P3 | 文档、示例、迁移体验 | 降低外部项目集成成本 |

---

## P0：阻塞级问题，必须先做

### P0-1. 将 `wagmi`、`viem`、`@tanstack/react-query` 调整为 `peerDependencies`

#### 问题

当前 `package.json` 将这些核心运行时库放在 `dependencies` 中，容易造成：

- 宿主应用装一套 `wagmi`
- `snk-wallet-kit` 自己再带一套 `wagmi`
- 最终运行时出现两套 `@wagmi/core`、两套 connector 状态源

这是当前 `ConnectorAlreadyConnectedError` 的根因之一。

#### 改造建议

- 将以下依赖移入 `peerDependencies`
  - `wagmi`
  - `viem`
  - `@tanstack/react-query`
- `dependencies` 中只保留真正必须由库自身私有持有的包
- README 中明确列出宿主需要自行安装的版本范围

#### 验收标准

- 安装 `snk-wallet-kit` 后，不再自动带入单独的 `wagmi` 运行时副本
- 宿主应用与库共享同一套 wagmi/react-query 上下文

---

### P0-2. 明确“唯一状态源”，停止库内外同时接管 EVM 连接生命周期

#### 问题

当前库在 `WalletCoreProvider` 模式下允许接收外部 `wagmiConfig`，但内部仍然会：

- `watchConnection`
- `wagmiConnect`
- `wagmiReconnect`
- 自己维护 `session`

这意味着：

- 外部 app 认为自己是状态拥有者
- `snk-wallet-kit` 内部也认为自己是状态拥有者

#### 改造建议

必须二选一，不要混合：

##### 方案 A（推荐）
将 `WalletCoreProvider` 定义为：

- **只消费外部 wagmi 状态**
- 不再创建或主导第二套 EVM 连接状态机
- UI 层调用连接时，也只是基于宿主提供的同一套 config 工作

##### 方案 B（次优）
如果坚持保留全托管模式：

- `WalletKitProvider` 全托管连接生命周期
- `WalletCoreProvider` 删除，或改成严格的内部低层组件，不对外暴露

#### 推荐结论

如果要对齐 RainbowKit 风格，优先选择 **方案 A**。

#### 验收标准

- EVM 连接只存在一套状态源
- 点击连接时不会出现同一 connector 被重复 connect / reconnect
- `WalletCoreProvider` 的职责边界清晰可解释

---

### P0-3. 删除库内自定义的 EVM 持久化重连模型，优先复用 wagmi 自身机制

#### 问题

当前库同时存在：

- 自定义 `PersistedSession`
- `app.autoReconnect`
- `wagmiReconnect()`
- 宿主侧可能还有自己的恢复逻辑

这会造成：

- 挂载时重复恢复连接
- session 与真实 connector 状态不一致
- 错误恢复时机难以推断

#### 改造建议

对 EVM：

- 删除或弱化 `PersistedSession` 的主导地位
- 不再以 `walletId + storageKey` 自己驱动恢复逻辑
- 尽量以 wagmi 官方的连接恢复机制为唯一来源

对 Solana：

- 可以保留自己的 session 抽象
- 但建议与 EVM 明确区分，不要共用一套容易误导的 reconnect 语义

#### 验收标准

- 页面首次挂载时，EVM 只恢复一次
- `autoReconnect` 不再和 wagmi 自身恢复机制重复打架
- 断开连接后，状态与 UI 都能一致复位

---

### P0-4. 收敛 Provider API，避免“开箱即用模式”和“高级接入模式”互相踩踏

#### 问题

现在公开的 Provider 设计会让使用者误以为：

- 我可以自己包 `WagmiProvider`
- 同时再让 `snk-wallet-kit` 自己管理连接
- 二者可以自然兼容

实际上不是。

#### 改造建议

明确拆分：

- `WalletKitProvider`：面向简单集成
- `WalletCoreProvider`：面向宿主已拥有 wagmi/react-query 的场景

同时文档上明确写出：

- 二者只能二选一作为“状态 ownership 模式”
- `WalletCoreProvider` 不负责创造第二套连接状态

#### 验收标准

- README 第一屏即可看清两种模式差异
- 用户不会再误以为可以任意叠加两套 provider 逻辑

---

## P1：高优先级，建议紧接着做

### P1-1. 简化配置模型，去掉语义重复项

#### 问题

当前存在容易混淆的配置：

- `evm.autoConnect`
- `sol.autoConnect`
- `app.autoReconnect`

但实际生效路径并不一致。

#### 改造建议

- 明确每个配置项只负责一个行为
- 如果 EVM 已完全交给 wagmi，`evm.autoConnect` 可以删除或标记废弃
- `app.autoReconnect` 应拆成更清晰的命名，或分别为 EVM / Solana 定义

#### 验收标准

- 用户看到配置名，就能准确知道是否影响挂载恢复、手动连接、断线重连
- README 中不需要大段解释“这个字段和那个字段的区别”

---

### P1-2. 重构 `WalletContext`，避免重复镜像 EVM session

#### 问题

当前 `WalletContext` 中既维护 UI 所需状态，又试图完整镜像底层 EVM 连接状态。

这会带来双向同步压力。

#### 改造建议

- 将 `WalletContext` 收敛为“展示与交互层上下文”
- EVM 的 account / chain / connected 尽量直接来源于宿主 wagmi 状态
- `snk-wallet-kit` 只补充跨链统一字段与 UI 行为状态
  - modal open
  - selected wallet intent
  - error presentation
  - current namespace preference

#### 验收标准

- EVM session 不再需要在多处 setState 镜像同步
- Wallet UI 与 wagmi hooks 读取到的状态始终一致

---

### P1-3. 明确 Solana 与 EVM 的抽象边界，不再假装两者完全同构

#### 问题

把 EVM 和 Solana 包成统一接口是有价值的，但两者底层模型并不相同。

如果过度统一，会带来很多“看似一致，实则行为不同”的 API。

#### 改造建议

- 保留统一入口：`connect/disconnect/signMessage/sendTransaction`
- 但在类型层面显式体现 namespace 差异
- 对切链、授权恢复、provider 检测等行为分别定义说明

#### 验收标准

- 类型提示能清楚说明某能力是否只支持 EVM 或 Solana
- 用户不会误认为所有 hook/配置在双链下完全等价

---

### P1-4. 重新定义 `WalletCoreProvider` 的官方定位

#### 建议定位

`WalletCoreProvider` 应该被定义为：

> 在宿主已经拥有 `QueryClientProvider` 与 `WagmiProvider` 的前提下，为 `snk-wallet-kit` UI 和 hooks 提供最薄的一层桥接上下文。

它不应该再被定义为：

> 可与任意外部 wagmi provider 混用、同时内部继续主导连接状态的高级版 Provider。

#### 验收标准

- `WalletCoreProvider` 的职责能用一句话说清楚
- 示例代码不再暗示“外部 provider + 内部状态机双控制”

---

## P2：重要但不阻塞，建议在架构收敛后处理

### P2-1. 评估是否保留自定义 WalletConnect connector

#### 问题

当前自定义 WalletConnect connector：

- 逻辑较重
- 维护成本高
- 存在 `@ts-nocheck`
- 后续容易随上游 API 演进而失稳

#### 改造建议

优先级顺序：

1. 评估能否直接复用 wagmi 官方 connector
2. 如果必须自定义，则缩小封装范围
3. 移除 `@ts-nocheck`
4. 为连接、断开、chain switch、stale session 加测试

#### 验收标准

- WalletConnect 行为与主流 wagmi 使用方式一致
- connector 实现可以通过类型检查

---

### P2-2. 增加最小可用测试矩阵

#### 当前缺口

未看到稳定的自动化测试与发布前验收机制。

#### 至少需要补的测试

- EVM injected 钱包单连接流程
- 已连接状态下重复点击连接
- 自动恢复与手动连接互斥
- WalletConnect connect / disconnect / reconnect
- Solana connect / disconnect
- 宿主使用 `useAccount` 与 kit UI 状态一致性

#### 推荐测试层次

- 单元测试：配置规范化、wallet descriptor、storage 行为
- 集成测试：provider 组合、连接流程
- 示例应用 smoke test：React / Next.js 最小集成

#### 验收标准

- 发布前至少能跑通一套 smoke test
- 修过的连接重复问题可被自动化回归覆盖

---

### P2-3. 梳理导出面，减少“半内部能力”外泄

#### 问题

当前导出层级较宽，容易把尚未稳定的内部抽象也一并暴露出去。

#### 改造建议

将导出面分为三层：

- 稳定公共 API
  - `WalletKitProvider`
  - `WalletCoreProvider`
  - `ConnectWalletButton`
  - `WalletSelectModal`
  - 公开 hooks
- 高级 API
  - 明确标注实验性
- 内部实现
  - 不对外导出

#### 验收标准

- 用户文档只需要介绍少量稳定 API
- 升级时不必对外长期兼容内部工具函数

---

## P3：体验与发布层优化

### P3-1. 重写 README 的接入章节

#### 必须明确说明

- 宿主必须安装哪些 peer dependencies
- 只应存在一套 wagmi runtime
- `WalletKitProvider` 与 `WalletCoreProvider` 的适用场景
- 不推荐的组合方式
- EVM 与 Solana 能力边界

#### 验收标准

- 新用户按 README 接入，不会默认踩中双 provider / 双 wagmi 问题

---

### P3-2. 增加 Migration Guide

如果本次改造涉及：

- peerDependencies 调整
- provider API 收敛
- reconnect 语义变化
- 配置项废弃

则需要补充迁移文档，至少包含：

- 旧写法
- 新写法
- 废弃项替代方案
- 常见错误排查

---

### P3-3. 提供两个官方示例工程

建议至少保留：

1. `next-wagmi-host`：宿主自己管理 wagmi
2. `quick-start`：最简单接入

这样最能验证 API 是否真的清晰。

## 最小重构里程碑

### Milestone 1：修复双 wagmi / 双连接问题

目标：

- 不再出现同一 connector 被重复连接
- 宿主与库共享同一套 EVM 状态

完成标准：

- 依赖边界调整完成
- `WalletCoreProvider` 不再主导第二套 EVM 状态机
- `ConnectorAlreadyConnectedError` 不再作为常见路径错误出现

### Milestone 2：形成稳定 API

目标：

- Provider 模式、配置语义、hooks 行为可预测

完成标准：

- README 示例能代表推荐用法
- 用户不需要阅读源码也能判断该用哪种 Provider

### Milestone 3：达到可发布质量

目标：

- 可持续维护、可回归测试、可做版本升级

完成标准：

- 至少具备 smoke test + migration guide + example apps

---

## 最终建议

如果只能先做一件事，优先做这三项：

1. **把 `wagmi/viem/react-query` 改成 peerDependencies**
2. **明确 EVM 只有一套状态源，停止库内外双重接管连接生命周期**
3. **去掉库内自定义的 EVM 重连持久化主导逻辑**

这三项做完，`snk-wallet-kit` 才算真正从“能用”迈向“适合作为通用 npm 库复用”。
